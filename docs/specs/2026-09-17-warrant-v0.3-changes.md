# Warrant draft 0.3: changes from the co-design review

Status: the agreed design changes and Trey's three decisions are incorporated. The combined draft is awaiting its final consistency review and Trey's ratification. No implementation plan or build is authorized.

## Prove the guidance helps before building the protected gate

Warrant should help agents make better architectural decisions, not just reject their work afterward. Fable's strongest criticism of draft 0.2 was that the checking machinery had more attention than the guidance that gives the product its reason to exist.

The build sequence now tests that guidance early. Once the map and advisory checks work, compare agents receiving Warrant's context with agents using the existing workflow. Keep the final checker and behavior tests the same. Count unnecessary new concepts, repair attempts, missed defects, and human interventions, including abandoned attempts.

Trey made this a stop-and-rethink checkpoint. If the guidance shows no benefit, we reconsider it before proceeding to the protected acceptance system. Mixed results go to him rather than being relabeled success. A later test uses new, held-out requests and the complete product, including a follow-on change to assess maintainability.

## Deliver context before the decision

An agent should not have to remember to ask for the map. The first supported harness adapter will deliver a bounded map summary at session start and relevant context alongside a submitted prompt.

The review caught a timing trap: a hook can run before a tool executes while its explanation reaches the model only with the completed tool's result. That cannot influence the edit already selected. The revised spec requires an observed run showing that the context reached the model before the decision it was meant to inform.

Missing, stale, truncated, or undelivered context stays distinguishable from a successful lookup that found no match. One verified adapter is enough to test the idea. More harness connections are not a prerequisite.

## Test whether the map finds the right thing

A new retrieval test asks whether Warrant can find an existing owner under ordinary words, handle ambiguous requests, recognize genuinely new responsibilities, and stay quiet on unrelated conversation. A confident wrong suggestion counts separately from a miss.

The test uses a small approved sample, not automatic access to private transcripts. Its criteria are set before the held-out measurement. Producing a report is not the same as passing it.

The spec also maps the vision's four opening problems to the mechanisms that help detect them. Context helps an agent find an existing cache or validator. Borrowed detectors supply applicable unused-code evidence. Behavior tests help detect authorization that does not control the tested action. None of those mechanisms proves the absence of all architectural mistakes.

## Make adoption less laborious

The census can start without a Warrant configuration. It proposes a starter manifest and candidate modules from existing package boundaries, directories, and import relationships. Those are observations for a person to judge, not automatic approval of the current mess.

Inherited problems can be drafted into one itemized exception batch. The human can sign that exact batch rather than hand-writing each record. Each item still names the specific findings, reason, scope, occurrence limits, and expiry. A new problem cannot inherit approval just because it resembles an old one.

## Keep two human approval actions

Trey approved a smaller system:

- Change the rules. This includes adopting a tool version or deliberately accepting a narrower checked claim.
- Accept a specific known violation. A single record can contain an exact, individually bounded batch.

Warrant does not need its own team-permission administration in v1. Existing protected system controls manage the first signer's trusted keys. There is no emergency switch that makes an unverified result green. A person can ship anyway, but the unchanged-policy receipt remains blocked. Deliberately changing the requirements is a different, visible decision.

Trey also chose visible advice as the default for measurable preferences. Architectural requirements still block. A preference can be made blocking or require human approval when he explicitly chooses that stricter behavior.

## Preserve the evidence guarantees

We considered reducing the information recorded about test inputs and rejected that reduction. Several inputs may share one authenticated record, but all relevant source, dependency, generated-input, and service identities must remain accounted for.

The proposed execution arrangement separates a protected controller from a worker running candidate code. The worker has no signing credential. That is a design to qualify using an existing runner, not a claim that a particular deployment is already safe or an instruction to build a new runner platform.

The spec also closes smaller contradictions around comparing several revisions, inherited-debt drafting, preference advice, and when the fast incremental-check target applies.

## What remains unproved

The compiler and retrieval investigations, actual hook delivery, early product comparison, and protected execution arrangement have not run. Their requirements are specified; their success is not assumed. The next human approval is ratification of the combined spec. An implementation plan and permission to build remain separate steps.
