# Prior art for Warrant

Research date: September 17, 2026  
Target: Warrant v1 as described in `docs/vision.md`, the selected sections of the v1 spec, and the W01 to W32 agent-builder wish list.

## Method and confidence labels

This survey uses current primary sources: official documentation, first-party repositories, release pages, and package registries. A version is "current" only when a release or registry source was read during this review. "Maintained" means the project had a release or first-party update in roughly the preceding year. "Maintenance-light" means the latest visible release or repository activity was older. A current documentation site, by itself, is not proof of active maintenance.

Each entry separates three kinds of statement:

- Verified facts are supported by the linked primary source.
- Inference for Warrant is an architectural conclusion drawn from those facts.
- Could not verify identifies an absence in the reviewed sources, not proof that a capability does not exist.

No reviewed architecture, lint, query, or policy tool emits a cryptographically signed compliance result unless the entry says otherwise. Most can run inside a CI system that signs or attests its surrounding job, but that is different from the tool binding its own policy, subject, evidence, and verdict into a verifiable receipt.

## 1. Architecture conformance testing

The common model in this family is architecture as tests. The rule is executable code or configuration inside the repository, the test runner supplies pass or fail, and ordinary code review governs changes to the rule. This is effective when humans own the test suite. In an agent-written repository, it also gives the implementer the pen for the constraint, its exclusions, and often its baseline.

### ArchUnit (Java)

Current status: ArchUnit 1.5.0 is the latest listed release and the release stream was active in 2026. ArchUnit imports Java bytecode and offers a fluent API for dependencies, layers, cycles, and custom conditions. A failure is an assertion error that includes the full rule text, violating classes, and source line numbers. [User guide](https://www.archunit.org/userguide/html/000_Index.html) [releases](https://github.com/TNG/ArchUnit/releases)

```java
noClasses().that().resideInAPackage("..domain..")
    .should().dependOnClassesThat().resideInAPackage("..web..");
```

Verified facts: rules are ordinary Java tests. `archunit_ignore_patterns.txt` suppresses violation messages by regular expression. `FreezingArchRule` records the current violations in a `ViolationStore`, reports only new violations later, removes repaired entries, and can be configured to "refreeze" the current state. The default store is plain text and line matching deliberately ignores line-number changes. Output is rich test text, not a documented standard machine interchange. [ignoring and freezing](https://www.archunit.org/userguide/html/000_Index.html#_ignoring_violations)

Inference for Warrant: borrow the readable fluent semantics, violation paths, and explicit no-new-violations migration mode. Reject an editable regex ignore file and unattended refreeze. A frozen set is useful evidence during adoption, but it is not authority and cannot become a gate receipt.

Could not verify: the reviewed sources do not document SARIF, signed results, a signer identity, expiry for suppressions, or a distinction between analysis completeness and compliance.

### ts-arch (TypeScript and JavaScript)

Current status: npm reports 5.4.1, published in December 2024. No newer package release was visible, so current maintenance is uncertain. It runs architecture assertions inside Jest or another test framework, using file, folder, slice, cycle, Nx graph, and PlantUML relationships. [repository](https://github.com/ts-arch/ts-arch/) [npm registry](https://registry.npmjs.org/tsarch)

```typescript
const rule = filesOfProject().inFolder("business")
  .shouldNot().dependOnFiles().inFolder("ui");
await expect(rule).toPassAsync();
```

Verified facts: rule failures flow through the host test framework. The project supports a slice model whose observed dependencies must adhere to a PlantUML diagram. [README](https://github.com/ts-arch/ts-arch/)

Inference for Warrant: borrow the ability to compare a program graph with a human-readable diagram, but keep the diagram derived from or checked against Warrant's program model. Reject a test-only verdict because a passing Jest assertion does not state the analyzed denominator or prove that resolution was complete.

Could not verify: a baseline, first-class suppression mechanism, signed artifacts, SARIF or JSON findings, governed exceptions, or an incremental invalidation model in the reviewed README.

### arch-unit-ts (TypeScript)

Current status: the `arch-unit-ts` package is 1.0.12, published in July 2026, and the first-party repository remained current. It mirrors ArchUnit's fluent class and package vocabulary over TypeScript, using ts-morph to build the model. [repository](https://github.com/manonMetral/arch-unit-ts) [npm registry](https://registry.npmjs.org/arch-unit-ts)

```typescript
noClasses().that().resideInAnyPackage("..application..")
  .should().dependOnClassesThat().resideInAnyPackage("..infrastructure..")
  .check(project.allClasses());
```

Verified facts: the library supports package dependency and layered-architecture tests and lets authors attach a `because(...)` explanation. Its own documentation warns that ts-morph can have difficulty reading some dependencies and prints a warning when that occurs. Reports are test failures and console warnings. [README](https://github.com/manonMetral/arch-unit-ts)

Inference for Warrant: borrow reasons on rules. Reject warning-only model gaps. The documented ts-morph failure mode is a direct example of why section 10 needs an independent `analysis: incomplete` facet.

Could not verify: structured external findings, a baseline, signed results, or a permission model for exceptions.

### Deptrac (PHP)

Current status: Packagist lists Deptrac 4.7.2 from September 15, 2026, so the project is actively maintained. Deptrac groups PHP classes into layers with collectors and checks a layer ruleset. [documentation](https://deptrac.github.io/deptrac/) [package metadata](https://repo.packagist.org/p2/deptrac/deptrac.json)

```yaml
deptrac:
  layers:
    - name: Controller
      collectors: [{ type: classLike, value: '.*Controller.*' }]
  ruleset:
    Controller: [Service]
```

Verified facts: the default table names the reason, source and target, file location, counts of violations, skipped violations, uncovered classes, warnings, and errors. Multiple formatters include Graphviz and machine-oriented formats. A ruleset may attach explicit skipped violations, and Deptrac treats an unmatched skip entry as an error, which catches stale exceptions. [overview](https://deptrac.github.io/deptrac/) [formatters](https://deptrac.github.io/deptrac/formatters/) [configuration](https://deptrac.github.io/deptrac/configuration/)

Inference for Warrant: borrow uncovered-class accounting and stale-suppression failure. Keep section 5's inventory denominator broader than Deptrac's class coverage, and require human-signed exception records rather than config entries the code author can add.

Could not verify: a cryptographically bound report, a no-new-violations baseline in the current docs, or exception ownership and expiry.

### jQAssistant

Current status: the current manual and schema are version 2.9, and 2.9.1 is the latest listed release. The project was active in 2026. jQAssistant scans software into Neo4j, enriches the graph with concepts, and checks Cypher constraints during the build. [manual](https://jqassistant.github.io/jqassistant/current/) [releases](https://github.com/jQAssistant/jqassistant/releases)

```xml
<constraint id="tests:must-assert">
  <cypher><![CDATA[
    MATCH (t:Test:Method)
    WHERE NOT (t)-[:INVOKES]->(:Assert:Method)
    RETURN t AS TestWithoutAssertion
  ]]></cypher>
</constraint>
```

Verified facts: any returned row is a violation. Results can be placed in console, XML, and report plugins, with configurable severities and build-failure thresholds. Empty concept results warn because a missing concept can invalidate downstream rules. Baseline management writes `jqassistant-baseline.xml`, suppresses matching prior results, removes repaired entries, and is intended for version control. [manual](https://jqassistant.github.io/jqassistant/current/)

Inference for Warrant: borrow the explicit graph-enrichment layer, the rule that a concept unexpectedly matching nothing is itself a problem, and a queryable graph. Reject general Cypher as Warrant's user policy language because its expressive power makes semantic policy diff and signer comprehension harder. The baseline is adoption evidence, not acceptance authority.

Could not verify: stable finding identities across arbitrary query changes, signed reports, per-exception authority, or expiry.

### NetArchTest (.NET)

Current status: NuGet's latest package is 1.3.2. The latest release is from 2021 and the repository page reports its last push in 2024, so it is maintenance-light. NetArchTest uses Mono.Cecil and a fluent .NET Standard API for naming, type, and dependency conventions. [repository](https://github.com/BenMorris/NetArchTest) [NuGet](https://www.nuget.org/packages/NetArchTest.Rules)

```csharp
Types.InCurrentDomain().That().ResideInNamespace("Domain")
  .ShouldNot().HaveDependencyOn("Web").GetResult();
```

Verified facts: `GetResult()` returns success plus failing types. Rules can be grouped into a `Policy`, evaluated lazily, and passed to a reporting mechanism. Custom predicates and conditions implement `ICustomRule`. [README](https://github.com/BenMorris/NetArchTest)

Inference for Warrant: borrow a small composable predicate-condition core and a first-class policy result object. Reject the assumption that an in-process object or unit-test pass identifies the exact source snapshot and tool build.

Could not verify: a built-in baseline, suppressions with lifecycle, standardized JSON or SARIF output, or signed results.

### Python imports, checked by Import Linter

Current status: PyPI reports 2.15, published in September 2026, so the project is actively maintained. It builds a Python import graph and checks forbidden, protected, layered, independence, and acyclic-sibling contracts. [configuration](https://import-linter.readthedocs.io/en/stable/get_started/configure/) [PyPI metadata](https://pypi.org/pypi/import-linter/json)

```toml
[[tool.importlinter.contracts]]
name = "Domain does not import web"
type = "forbidden"
source_modules = ["app.domain"]
forbidden_modules = ["app.web"]
```

Verified facts: contracts live in INI or TOML and can be selected by stable contract id. `ignore_imports` suppresses matching edges; unmatched ignore expressions are errors by default, with optional warn or none behavior. The CLI has a cache and `--no-cache`, but it checks the requested contract set rather than emitting a documented diff receipt. [contract types](https://import-linter.readthedocs.io/en/stable/contract_types/) [running the linter](https://import-linter.readthedocs.io/en/stable/get_started/run/)

Inference for Warrant: borrow named contract types, contract selection, and unmatched-ignore errors. Reject edge strings as the durable exception identity when symbol or module meaning can change.

Could not verify: a documented machine result schema, signing, policy authority, or a no-new-violations mode.

### pytest-archon (Python)

Current status: PyPI reports 0.0.7 from September 2025. The repository is active enough to have current documentation, but the sparse release history makes maintenance uncertain. It defines import-boundary rules as pytest tests and supports top-level, type-checking, direct, and transitive import choices. [repository](https://github.com/jwbargsten/pytest-archon/) [PyPI metadata](https://pypi.org/pypi/pytest-archon/json)

```python
archrule("domain").match("app.domain*") \
    .should_not_import("app.web*").check("app")
```

Verified facts: failures are pytest failures. Rules accept explicit exclusions and `may_import` allowances, and can use custom predicate functions. Whoever may merge the architecture-test source can grant those allowances; no separate approver is part of the documented mechanism. [README](https://github.com/jwbargsten/pytest-archon/)

Inference for Warrant: borrow the explicit switches for direct versus transitive and runtime versus type-checking imports. Warrant should record those semantics in the effective policy and receipt rather than leaving them as test helper arguments.

Could not verify: a separate baseline or report format, signed output, structured findings beyond pytest integrations, governed suppressions, or incremental invalidation in the reviewed README.

### What architecture-as-tests gets right and misses

Verified facts: every tool above puts an executable architectural check close to the code and makes it part of the ordinary test or build loop. Several support staged adoption by freezing or baselining existing failures. Several also let the same repository edit the rule, the ignore, and the baseline. [ArchUnit freezing](https://www.archunit.org/userguide/html/000_Index.html#_freezing_arch_rules) [jQAssistant baseline](https://jqassistant.github.io/jqassistant/current/) [Import Linter ignores](https://import-linter.readthedocs.io/en/stable/contract_types/)

Inference for Warrant: architecture as tests is the right authoring and feedback model but the wrong authority model for agent-written code. Warrant should make contract checks feel like tests while keeping trust roots, signed rulings, receipt production, and integration-gate execution outside the candidate's discretionary control. Section 7 already reflects the first half. Sections 10 and 11 supply the missing second half.

## 2. Dependency and boundary linting for JavaScript and TypeScript

### dependency-cruiser

Current status: npm reports 18.3.1, published September 14, 2026, so the project is actively maintained. It extracts JavaScript and TypeScript module dependencies and validates `forbidden`, `allowed`, and `required` rules. [CLI](https://github.com/sverweij/dependency-cruiser/blob/main/doc/cli.md) [npm registry](https://registry.npmjs.org/dependency-cruiser)

```json
{
  "forbidden": [{
    "name": "no-domain-to-ui",
    "severity": "error",
    "from": { "path": "^src/domain" },
    "to": { "path": "^src/ui" }
  }]
}
```

Verified facts: `--validate` applies the configuration. The default error reporter exits nonzero for error-severity violations; JSON exposes the internal graph and violations; HTML and other renderers provide summaries and rule context. `--ignore-known` reads `.dependency-cruiser-known-violations.json`. The `baseline` reporter or `depcruise-baseline` command can regenerate that file, after which matching violations are downgraded to ignored. [CLI and baseline](https://github.com/sverweij/dependency-cruiser/blob/main/doc/cli.md) [rules](https://github.com/sverweij/dependency-cruiser/blob/main/doc/rules-reference.md)

Inference for Warrant: borrow the mature dependency graph, rule import path in section 15.3, stable rule names, comments that explain intent, and its machine graph format as an instrument. Reject `severity: ignore` and a regenerable known-violations file as gate authority. A Warrant importer should preserve rule semantics and produce draft contracts, not silently convert ignores into approved exceptions.

Could not verify: native SARIF in the reviewed current CLI page, signed output, exception owners or expiry, and an incremental invalidation explanation.

### eslint-plugin-boundaries

Current status: npm reports 7.2.0 from August 2026, so the project is actively maintained. The plugin classifies files into architectural elements and applies ordered dependency policies. Its current canonical rule is `boundaries/dependencies`; it also reports unknown files, unknown dependencies, and dependencies on ignored files. [rules](https://www.jsboundaries.dev/docs/rules/) [npm registry](https://registry.npmjs.org/eslint-plugin-boundaries)

```javascript
"boundaries/dependencies": [2, {
  default: "disallow",
  rules: [{
    from: { element: { type: "feature" } },
    allow: { to: { element: { type: ["domain", "shared"] } } }
  }]
}]
```

Verified facts: policies are ordered and the last matching policy wins. The rule emits detailed ESLint diagnostics naming the selected elements and matched rule. ESLint can emit JSON and can disable plugin rules inline, while `--no-inline-config` prevents candidate comments from changing rule behavior and unused-disable reporting exposes stale directives. [dependency rule](https://www.jsboundaries.dev/docs/rules/dependencies/) [ESLint CLI](https://eslint.org/docs/latest/use/command-line-interface) [ESLint suppressions](https://eslint.org/docs/latest/use/configure/rules#disabling-rules)

Inference for Warrant: borrow explicit unknown-file and unknown-dependency checks, element captures, and the section 15.3 importer. Reject order-dependent policy semantics for section 7.6. Warrant should also run imported ESLint rules with inline suppression disabled unless a signed exception explicitly permits one.

Could not verify: a plugin-specific baseline, signed results, or an exception authority distinct from whoever can edit ESLint configuration.

### eslint-plugin-import

Current status: npm reports 2.32.0 from June 2025. The project remains widely used, but the package release is older than a year, so current maintenance is uncertain. Its architecture-relevant `import/no-restricted-paths` rule defines source zones, forbidden targets, exceptions, and messages. [rule](https://github.com/import-js/eslint-plugin-import/blob/main/docs/rules/no-restricted-paths.md) [npm registry](https://registry.npmjs.org/eslint-plugin-import)

```json
{
  "zones": [{ "target": "./client", "from": "./server", "except": ["./server/schema"] }]
}
```

Verified facts: `from` matches the resolved imported file, not the spelling of the import. Violations and machine output use ESLint's diagnostics and JSON formatter. Exceptions may be expressed in a zone or with ordinary ESLint disable comments. Whoever may merge the ESLint configuration or source comment grants them; no independent approval authority is documented. [restricted paths](https://github.com/import-js/eslint-plugin-import/blob/main/docs/rules/no-restricted-paths.md) [ESLint output](https://eslint.org/docs/latest/use/command-line-interface)

Inference for Warrant: borrow resolver-aware restricted zones as an instrument and migration source. Reject path zones as the final contract vocabulary because they describe file layout rather than module responsibility, interface, effect, or capability.

Could not verify: a baseline, cryptographic output, or a governed exception lifecycle.

### eslint-plugin-import-x

Current status: npm reports 4.17.1 from June 2026, so the fork is actively maintained. It describes itself as a lighter and faster fork of `eslint-plugin-import` and carries the analogous `import-x/no-restricted-paths` rule. [repository and rule](https://github.com/un-ts/eslint-plugin-import-x/blob/master/docs/rules/no-restricted-paths.md) [npm registry](https://registry.npmjs.org/eslint-plugin-import-x)

```javascript
"import-x/no-restricted-paths": ["error", {
  zones: [{ target: "./browser", from: "./server" }]
}]
```

Verified facts: targets, forbidden sources, `except`, and custom messages have the same resolved-path model as the original plugin. Reporting, inline suppression, and JSON output are supplied by ESLint. Whoever may merge the ESLint configuration or source comment grants an exception; no independent approval authority is documented. [rule](https://github.com/un-ts/eslint-plugin-import-x/blob/master/docs/rules/no-restricted-paths.md) [ESLint output and suppression controls](https://eslint.org/docs/latest/use/command-line-interface)

Inference for Warrant: prefer whichever import plugin already exists in a repository, pin it as an instrument, and normalize its evidence. Do not make Warrant's semantics depend on choosing one fork.

Could not verify: a baseline, signed output, or exception governance beyond ESLint configuration and comments.

### Nx `@nx/enforce-module-boundaries`

Current status: npm reports Nx 23.2.1 from September 2026, and the documentation covers both the open-source JavaScript/TypeScript ESLint rule and a language-agnostic Enterprise conformance rule. The mechanism uses project tags over the Nx graph. [documentation](https://nx.dev/docs/features/enforce-module-boundaries) [npm registry](https://registry.npmjs.org/nx)

```javascript
"@nx/enforce-module-boundaries": ["error", {
  depConstraints: [{
    sourceTag: "scope:admin",
    onlyDependOnLibsWithTags: ["scope:admin", "scope:shared"]
  }]
}]
```

Verified facts: the ESLint rule checks code imports and package dependencies. Nx Conformance checks the complete project graph with the same tag constraint model but requires an Enterprise plan. Untagged projects cannot depend on other projects unless the policy explicitly allows all tags. Violations are ESLint or conformance failures. Required exceptions live in `allow`, constraint patterns, or ESLint suppressions and are granted by whoever may merge those files; no independent approver is documented. [module boundaries](https://nx.dev/docs/features/enforce-module-boundaries)

Inference for Warrant: borrow multidimensional project tags, project-graph ingestion, and a census importer. Reject the idea that tags alone express ownership or capabilities. Preserve tags as selectors or observed metadata, then compile them into typed Warrant contracts.

Could not verify: a first-party baseline, a stable standalone finding schema for the ESLint rule beyond ESLint JSON, signed results, or human-scoped waivers.

### Sheriff

Current status: `@softarc/sheriff-core` is 0.19.6 from September 2025. The project has current documentation, but the package release is approximately a year old, so maintenance is uncertain. Sheriff detects modules, assigns tags, and enforces dependency rules through lint integration. [dependency rules](https://github.com/softarc-consulting/sheriff/blob/main/docs/docs/dependency-rules.md) [npm registry](https://registry.npmjs.org/%40softarc%2Fsheriff-core)

```typescript
export const config = {
  modules: { "src/<domain>/<type>": ["domain:<domain>", "type:<type>"] },
  depRules: { "domain:*": [sameTag], "type:feature": ["type:data"] }
};
```

Verified facts: Sheriff supports automatic or manual tags, wildcard dimensions, a `sameTag` function, root-module rules, and incremental adoption through automatic `noTag` classification. A prohibited dependency triggers a lint error. [dependency rules](https://github.com/softarc-consulting/sheriff/blob/main/docs/docs/dependency-rules.md)

Inference for Warrant: borrow captured, multidimensional tags and a migration mode that leaves unclassified code visible. Reject policy functions in the signed contract layer because semantic diff of arbitrary functions is not reliably inspectable.

Could not verify: standardized machine output independent of its lint host, a baseline, signed results, or exception ownership and expiry.

### Turborepo boundaries

Current status: npm reports Turborepo 2.10.13 from September 2026. The `turbo boundaries` command is explicitly experimental. It checks workspace-package escapes, undeclared package dependencies, and tag allow or deny policies, including transitive dependencies. [boundaries](https://turborepo.dev/docs/reference/boundaries) [npm registry](https://registry.npmjs.org/turbo)

```json
{
  "boundaries": {
    "tags": { "public": { "dependencies": { "deny": ["internal"] } } }
  }
}
```

Verified facts: a package can carry tags, and rules can constrain its dependencies or dependents by tag or package name. The command notifies on violations, including imports outside a package and imports of undeclared dependencies. [boundaries](https://turborepo.dev/docs/reference/boundaries)

Inference for Warrant: borrow detection of dependency declarations that disagree with actual imports and the option to apply tag restrictions transitively. Treat the command as a version-pinned instrument until its experimental semantics stabilize.

Could not verify: structured JSON or SARIF output, suppressions, a baseline, a stable finding identity, or signed output in the reviewed current page.

### Madge

Current status: npm reports 8.0.0 from August 2024, and no newer package was visible, so Madge is maintenance-light. It builds dependency graphs and detects circular dependencies for JavaScript, TypeScript, and several related formats. [repository](https://github.com/pahen/madge) [npm registry](https://registry.npmjs.org/madge)

```json
{ "tsConfig": "./tsconfig.json", "excludeRegExp": ["generated/"] }
```

Verified facts: `madge --circular` reports cycles, while its API returns arrays and graph objects and can render DOT or images. Configuration can exclude paths or filter dependencies. The documentation warns that skipped or unresolved files may disappear unless warnings or debug output are requested. [README](https://github.com/pahen/madge)

Inference for Warrant: use Madge only as optional graph or cycle evidence, never as the completeness authority. Its documented skipped-file behavior supports HC3: unresolved inputs must become `analysis: incomplete`, not a clean graph.

Could not verify: a general architecture rule language, SARIF, a governed suppression model, a baseline, or signed output.

### Knip

Current status: npm reports 6.36.0 published September 16, 2026, so Knip is actively maintained. It analyzes unused files, exports, types, dependencies, binaries, unresolved imports, and representative cycle paths. [reporters](https://knip.dev/features/reporters) [npm registry](https://registry.npmjs.org/knip)

```json
{
  "rules": { "cycles": "error" },
  "cycles": { "allow": [["src/a.ts", "src/b.ts"]] },
  "ignoreFiles": ["src/generated/**"]
}
```

Verified facts: Knip has JSON, SARIF 2.1.0, Code Climate, GitHub Actions, Markdown, and custom reporters. The JSON schema groups issues by file with locations; its SARIF can be uploaded to GitHub code scanning. It offers targeted ignore options, exact allowed cycle paths, production mode, watch mode, and a conservative file-analysis cache. [reporters](https://knip.dev/features/reporters) [configuration](https://knip.dev/reference/configuration) [CLI](https://knip.dev/reference/cli)

Inference for Warrant: borrow Knip rather than duplicate dead-code and cycle analysis. Ingest SARIF or JSON with the instrument version and report digest, surface its non-exhaustive cycle-path limitation, and never convert `ignore` or `cycles.allow` into trusted Warrant authority automatically.

Could not verify: a no-new-violations baseline, cryptographic binding to a source tree, or human authorization for ignores.

### Family conclusion

Verified facts: JavaScript and TypeScript already have mature graph extraction, path and tag policies, unknown-file checks, JSON, and SARIF. They also have many candidate-editable escape hatches: inline ESLint comments, ignored paths, allowed tag edges, and known-violation files. [ESLint controls](https://eslint.org/docs/latest/use/command-line-interface) [dependency-cruiser baseline](https://github.com/sverweij/dependency-cruiser/blob/main/doc/cli.md) [Knip reporters](https://knip.dev/features/reporters)

Inference for Warrant: section 15.3 is justified, but importers must create drafts, not authority. Section 9 should prefer native machine output, with SARIF as the first interchange where supported. The new work is not another dependency linter. It is the effective-policy compiler, completeness accounting, governed exception layer, and receipt that binds these instruments to the exact candidate.

## 3. Build-system-enforced visibility

Visibility built into a compiler or build graph has a stronger failure mode than a separate linter. An illegal edge is not merely reported after the program is resolved. It is rejected by the same mechanism that decides which target, package, module, or item exists. This removes one class of analyzer-to-build disagreement. It does not establish that every architectural obligation can or should be encoded as visibility.

### Bazel visibility and `package_group`

Current status: Bazel 9 is the current LTS line, and 9.3.0 release-candidate material was published in September 2026, so Bazel is actively maintained. [Bazel 9 announcement](https://blog.bazel.build/2026/01/20/bazel-9.html) [9.3.0 release candidate](https://releases.bazel.build/9.3.0/rc1/index.html)

```python
package_group(name = "core_clients", packages = ["//apps/..."])
cc_library(name = "core", visibility = [":core_clients"])
```

Verified facts: a target's `visibility` allowlist can name a package, its subpackages, a `package_group`, public, or private. Bazel checks visibility when one target names another in an attribute and produces a build-graph error. `package_group` centralizes a reusable client set. Bazel also documents load visibility for `.bzl` files and newer transitive visibility controls. [visibility](https://bazel.build/concepts/visibility)

Exceptions and incremental behavior: the exception is a broader visibility declaration or package-group membership. Bazel's ordinary incremental build graph rechecks affected targets, but the visibility page documents no "allow existing violations" baseline. Authority is whoever can merge the BUILD or package-group change.

Inference for Warrant: borrow native target identity, package groups, private-by-default interfaces, and graph-authoritative resolution.
Warrant should recognize Bazel visibility as strong evidence for dependency contracts and separately classify any widening of the visibility set. It should not replace effects, evidence requirements, or capability links with BUILD visibility.

> Could not verify: a portable machine result schema, signed visibility verdict, or native exception lifecycle with owner, reason, and expiry.
> The reviewed visibility documentation defines neither artifact.

### Buck2 visibility and `within_view`

Current status: Buck2 uses dated rolling releases, including a June 15, 2026 release, and remains actively maintained. [releases](https://github.com/facebook/buck2/releases) [visibility](https://buck2.build/docs/concepts/visibility/)

```python
java_library(
  name = "payments",
  visibility = ["//apps/checkout:"],
  within_view = ["//platform:ledger"],
)
```

Verified facts: `visibility` says which targets may depend on a target. `within_view` says which targets the current target may depend on, and takes precedence when the two lists conflict. Empty visibility defaults to the same BUCK file; `PUBLIC` opens it globally. `buck2 audit visibility` checks the transitive dependency graph. [visibility and audit](https://buck2.build/docs/concepts/visibility/)

Exceptions and incremental behavior: a target pattern can be added to either allowlist. This is a policy edit, not a separately governed waiver. Buck2 incrementally rebuilds its graph, but no baseline mode is documented on the reviewed visibility page.

Inference for Warrant: borrow the two-sided vocabulary. It maps cleanly to Warrant's interface consumers and dependency allowlists.
When both producer and consumer constraints exist, Warrant should expose which side blocked the edge rather than flattening them into one generic violation.

> Could not verify: signed output, structured visibility findings independent of Buck2's command output, or expiring exceptions.
> The reviewed Buck2 page documents only the visibility model and audit command.

### Go `internal/` directories

Current status: the current Go release endpoint reports Go 1.27.1 from August 2026, so the language is actively maintained. [current version](https://go.dev/VERSION?m=text) [module layout](https://go.dev/doc/modules/layout)

```text

```

Verified facts: packages under an `internal` directory cannot be imported from outside the parent tree that contains that directory. Exceptions and incremental behavior: there is no per-import exception. Moving the package, changing the tree boundary, or adding an exported facade changes the architecture. Ordinary Go build caching is incremental, but there is no architectural baseline.

Inference for Warrant: borrow the convention as compiler-enforced evidence and as a census signal.
Reject it as the sole contract model because directory ancestry cannot express named consumers, effects, state writers, or cross-language edges.

### Rust visibility and workspace crates

Current status: Rust 1.98.1 was released in September 2026, so the language is actively maintained. [release](https://blog.rust-lang.org/2026/09/03/Rust-1.98.1/) [reference](https://doc.rust-lang.org/reference/visibility-and-privacy.html)

```rust
pub(crate) fn apply_ruling() {}
pub(in crate::policy) struct EffectivePolicy;
```

Verified facts: Rust items are private by default. `pub(crate)`, `pub(super)`, and `pub(in path)` restrict visibility to the crate, parent module, or named ancestor scope. The compiler checks every path, import, type, and expression for a valid access. Public re-exports can expose an item through a controlled path while its implementation path remains inaccessible. [visibility and privacy](https://doc.rust-lang.org/reference/visibility-and-privacy.html)

Exceptions and incremental behavior: an author changes the visibility or introduces a public re-export. A workspace crate is also a hard compilation and dependency boundary, but `pub(crate)` stops at that crate. Cargo and rustc incrementally rebuild affected units; there is no violation baseline.

Inference for Warrant: Warrant's own Rust crates should make contract boundaries true in Rust first, then let Warrant verify and explain the same boundary at the repository level.
A contract whose enforcement can be lowered to `pub(crate)` or a private module should prefer that native control. Warrant remains necessary for cross-crate, cross-language, evidence, effect, and authority rules.

> Could not verify: a portable machine diagnostic schema, a compiler-native human-approved temporary visibility exception, or a signed architecture receipt.
> The reviewed Rust reference defines access semantics only.

### Java modules

Current status: the JDK 26 project is current in 2026, and the Java module system remains part of the language and runtime. [JDK 26](https://openjdk.org/projects/jdk/26/) [Java Language Specification](https://docs.oracle.com/javase/specs/jls/se25/html/jls-7.html)

```java
module app.core {
    requires app.ledger;
    exports app.core.api;
    exports app.core.testing to app.core.tests;
}
```

Verified facts: `requires` declares module dependencies. `exports` makes public and protected types in a package accessible to other modules; `exports ... to` grants access only to named friend modules. A public type in a non-exported package remains inaccessible outside its module. The compiler must respect module resolution, and resolution failure is a compile-time error. `opens` is distinct because it grants reflective runtime access rather than ordinary compile-time access. Exceptions and incremental behavior: a module descriptor can add a friend export, unqualified export, requirement, or open package. That edit changes the effective architecture directly. The module system has no no-new-violations baseline or signed approval record.

Inference for Warrant: borrow separate dependency, export, qualified friend, and reflective-open edges. Warrant should classify `exports p to m` becoming `exports p` as a clear widening and should never treat `opens` as equivalent to an ordinary API.

Could not verify: a portable machine finding schema, cryptographic result binding, or governed temporary exceptions in the module system itself.

### Family conclusion

Inference for Warrant: these engines already do the expensive parsing and graph or pattern work. Verified facts: the default `Code-Review` scale distinguishes `+1` from `+2`, where `+2` is final approval. A typical `Verified` label uses `-1`, `0`, and `+1` for CI. Access controls assign groups the ranges they may vote; projects can reserve `Verified +1` for CI and `Code-Review +2` for human approvers. [labels](https://gerrit.googlesource.com/gerrit/+/HEAD/Documentation/config-labels.txt) [access control](https://gerrit.googlesource.com/gerrit/+/HEAD/Documentation/access-control.txt)

Exceptions and incremental behavior: a new patch set is a new candidate for votes and submit requirements, subject to configured copy conditions. Administrators define who may vote, remove a vote, or submit. Gerrit's authenticated record is structured and auditable but is not a detached cryptographic statement about the exact architecture policy.

Inference for Warrant: this is the clearest governance precedent for the four-facet verdict. `Verified +1` means the machine established something. `Code-Review +2` means an authorized person ratified something. Neither should impersonate the other. Warrant should expose compliance and approval separately, then let Gerrit or another coordinator compose them.

Could not verify: a Gerrit-native signed, offline-verifiable label vote or expiring finding-scoped exception artifact.

### Family conclusion

Inference for Warrant: policy engines show how to evaluate, admission systems show how to fail closed, quality gates show how to adopt incrementally, and code hosts show how to compose machine status with human authority. Warrant should reuse all four patterns without collapsing them. The closest control-plane borrowing is Gerrit's separate machine and human labels. The strongest policy-integrity borrowing is OPA's out-of-band verification of signed bundles. Neither supplies Warrant's semantic program model or exact-tree architecture receipt.

## 6. Supply-chain attestation

### In-toto Statement v1, layouts, and DSSE

Current status: the in-toto Attestation Framework's current release is 1.2.0 from March 2026, and the reference in-toto implementation's current release is 3.1.0 from May 2026. Both projects remained active in 2026. [attestation release](https://api.github.com/repos/in-toto/attestation/releases/latest) [reference implementation release](https://api.github.com/repos/in-toto/in-toto/releases/latest)

```json
{
  "_type": "https://in-toto.io/Statement/v1",
  "subject": [{ "name": "snapshot", "digest": { "gitTree": "..." } }],
  "predicateType": "https://warrant.dev/attestation/receipt/v1",
  "predicate": {}
}
```

Verified facts: Statement v1 binds immutable subjects by digest to a URI-identified predicate type. The Statement is a data model, not a signature envelope. Classic in-toto layouts go further: a project owner signs ordered steps, authorized functionary keys, thresholds, commands, and expected material or product rules. Link metadata from the functionaries is then verified against that layout. [Statement v1](https://github.com/in-toto/attestation/blob/main/spec/v1/statement.md) [in-toto specification](https://github.com/in-toto/specification/blob/master/in-toto-spec.md)

Native rule example: an in-toto layout may require ordered artifact rules such as `MATCH`, `CREATE`, `DELETE`, `MODIFY`, `REQUIRE`, and `DISALLOW`. The specification warns that an implicit `ALLOW *` remains unless the author closes the rule list with `DISALLOW *`. [artifact rules](https://github.com/in-toto/specification/blob/master/in-toto-spec.md)

Exceptions and baseline: changing expected steps or artifacts requires a newly signed layout. Delegated sublayouts and threshold functionaries express authority, but layouts have no finding-scoped waiver or no-new-violations baseline.

DSSE: a DSSE envelope signs a pre-authentication encoding of `payloadType` and the exact payload bytes, avoiding JSON canonicalization. It carries `payload`, `payloadType`, and one or more signatures. [DSSE](https://github.com/secure-systems-lab/dsse) [design rationale](https://github.com/secure-systems-lab/dsse/blob/master/background.md)

Inference for Warrant: keep Statement v1 and typed predicates. Borrow signed-policy semantics and signer thresholds for high-risk rulings. Reject classic layouts as Warrant's contract language because they govern pipeline steps and file flow, not semantic module, effect, state, and capability obligations.

Could not verify: a standard in-toto verifier that will automatically understand Warrant's custom predicate plus detached OpenSSH signature. That construction is structurally an in-toto Statement, but it is not a DSSE or Sigstore bundle.

### SLSA provenance and verification summaries

Current status: SLSA 1.2 is the current approved specification. Its build track defines provenance and progressively stronger hosted and hardened build-platform requirements. [SLSA 1.2](https://slsa.dev/spec/v1.2/) [build track](https://slsa.dev/spec/v1.2/build-track-basics)

```json
{
  "predicateType": "https://slsa.dev/verification_summary/v1",
  "predicate": {
    "verifier": { "id": "...", "version": { "warrant": "..." } },
    "policy": { "uri": "...", "digest": { "sha256": "..." } },
    "inputAttestations": [],
    "verificationResult": "PASSED"
  }
}
```

Verified facts: provenance records where, when, and how an artifact was produced; it does not prove architectural quality. A Verification Summary Attestation (VSA) is much closer to Warrant's receipt. It binds subject digests, verifier identity and component versions, exact policy URI and recommended digest, input-attestation digests, verification time, and a `PASSED` or `FAILED` result. Verification checks the envelope signature, subject, predicate type, signer-verifier pairing, resource URI, result, and expected properties. [provenance](https://slsa.dev/spec/v1.2/provenance) [VSA](https://slsa.dev/spec/v1.2/verification_summary)

Exceptions and baseline: SLSA leaves exceptions and policy selection to the consumer and its trusted verifier or signer pairs. SLSA levels are supply-chain maturity claims, not a source-quality baseline.

Inference for Warrant: add an explicit VSA compatibility story. A gate receipt can either emit a companion VSA or define a deterministic mapping from Warrant's richer predicate. Reuse `verifier.version`, `policy.digest`, `inputAttestations`, and the prescribed verification order. Keep the four Warrant facets because VSA's binary result cannot express simultaneous violation, incomplete analysis, stale evidence, and pending approval.

Could not verify: a VSA field that directly represents Warrant's four independent facets. That remains a custom predicate concern.

### Sigstore, cosign, Rekor, and gitsign

[cosign release](https://api.github.com/repos/sigstore/cosign/releases/latest) [Rekor release](https://api.github.com/repos/sigstore/rekor/releases/latest) [gitsign release](https://api.github.com/repos/sigstore/gitsign/releases/latest)

Verified facts: Sigstore keyless signing uses a short-lived key tied to an OIDC identity through Fulcio and records signing evidence through Rekor. Could not verify: any Sigstore primitive that proves the signed test or analyzer ran honestly. It proves who signed which bytes, subject to the trust root.

### Git and OpenSSH signing

Current status: Git's current documentation line is 2.55.0. The reviewed OpenSSH manual documents arbitrary-data signing, allowed signers, namespaces, key validity windows, and historical verification. [Git signature format](https://git-scm.com/docs/gitformat-signature) [Git configuration](https://git-scm.com/docs/git-config/2.53.0) [OpenSSH `ssh-keygen`](https://man.openbsd.org/ssh-keygen.1)

```bash

  -I signer -f allowed_signers -s ruling.json.sig < ruling.json
```

Verified facts: Git can embed SSH signatures in commits and annotated tags. `gpg.ssh.allowedSignersFile` maps principals to trusted public keys. `ssh-keygen -Y sign` and `-Y verify` sign arbitrary bytes under a namespace; allowed-signers entries can constrain namespace and key-validity windows, and verification can use a specified historical time. [Git signature format](https://git-scm.com/docs/gitformat-signature) [allowed signers](https://git-scm.com/docs/git-config/2.53.0) [OpenSSH manual](https://man.openbsd.org/ssh-keygen.1)

Exceptions and baseline: Git and OpenSSH supply identity and integrity only. The signed Statement must define Warrant's scope, expiry, supersession, policy digest, and finding identities.

Inference for Warrant: section 11's namespace-per-ruling-kind and out-of-candidate allowed-signers root are sound uses of these primitives. Keep rulings as scoped Statements instead of commits or tags. State plainly that SSH signing has no transparency log and no independently witnessed timestamp.

Could not verify: a stock `ssh-keygen` path for DSSE envelope verification. This is the real tradeoff behind the spec's detached-signature choice.

Inference for Warrant: reuse Statement v1, VSA-compatible policy and verifier fields, typed predicates, subject digests, input-attestation digests, out-of-band trust roots, and established envelope options. ## 7. Fitness functions and architecture governance literature

### Evolutionary architecture fitness functions

Verified facts: Building Evolutionary Architectures, second edition, defines evolutionary architecture as guided, incremental change across multiple dimensions. Fitness functions are objective measures intended to prevent chosen architectural characteristics from degrading. The authors distinguish automated and manual, atomic and holistic, and triggered and continual fitness functions. [second-edition chapter](https://www.thoughtworks.com/content/dam/thoughtworks/documents/books/bk_building_evolutionary_architectures_second_edition_free_chapter.pdf) [fitness-function katas](https://evolutionaryarchitecture.com/ffkatas/)

Version, syntax, and output: a current software version is not applicable to a book and architectural concept. Fitness functions are a classification for executable checks, not one native rule language or report schema. The literature does not define exception authority, signing, or a baseline format.

Inference for Warrant: Warrant is an architectural fitness-function engine with stronger evidence and authority semantics. It embodies the book rather than contradicting it. It should use the vocabulary explicitly, while refusing to turn a subjective characteristic such as "maintainable" into a deterministic rule until that characteristic is lowered into a checkable obligation or labeled judgment. The book does not supply structured findings, governed exceptions, signed receipts, or exact-tree binding.

### Architecture decision records

Verified facts: Michael Nygard's original ADR proposal keeps small repository-local records for architecturally significant decisions. Each record has title, context, decision, status, and consequences. A reversed decision remains in history but is marked superseded. [Nygard's ADR proposal](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions)

```text
Status: Superseded by ADR-0042
Decision: All outbound mail uses the mail adapter.
Consequences: Direct provider calls are prohibited.
```

Version, reporting, and authority: ADRs are a document pattern, not a versioned analyzer. The record template above is the native syntax. The method does not prescribe machine findings, a baseline, signature verification, or who may approve an exception; a repository's governance supplies those controls.

Inference for Warrant: a ruling is a cryptographically bound, executable ADR. Borrow the durable rationale and supersession chain, but do not make every ADR enforceable. Only a ratified ruling whose scope, policy digest, candidate range, and signature verify should alter the gate. Ordinary ADR prose remains context, not authority.

## Gaps no prior tool fills

The honest argument for building Warrant is the intersection. Architecture test libraries and dependency linters already enforce edges. CodeQL, Semgrep, ast-grep, Joern, SCIP, and compilers already supply program facts. SARIF already carries findings. In-toto, OPA, SLSA VSA, SSH, Sigstore, and GitHub attestations already carry signed policy, identity, subject digests, and verification summaries. Gerrit and GitHub already combine machine status with human authority. Kazi, CATES, Coding Ethos, Sonar, and agent hooks already address parts of AI-written-code governance.

No mature tool reviewed here was verified to combine all of these properties:

1. a compiler-aligned, language-spanning program model that can express modules, interfaces, effects, state owners, and capability links;
2. an explicit inventory denominator and a first-class `incomplete` result when required analysis could not run;
3. deterministic contracts plus external test and instrument evidence bound to the exact integrated tree;
4. agent-readable findings that explain the smallest cause, valid interface, and focused proof;
5. human-only, signed, scoped, expiring policy widening and exceptions, with semantic policy diff;
6. a portable verdict whose compliance, completeness, evidence, and approval facts remain separately verifiable.

The strongest argument that part of Warrant already exists is SLSA VSA plus in-toto. VSA already expresses "this exact subject was evaluated by this verifier under this exact policy digest using these input attestations, with this result." Classic in-toto layouts already express signed policy, authorized functionaries, thresholds, and verified evidence flow. Warrant should not rebuild or claim novelty for that generic layer.

The next-strongest overlap is operational. Coding Ethos already combines source-aware policy, hooks, CEL, SARIF, and agent remediation. Kazi already parses structured evidence, gates on live and static predicates, and prevents an agent from weakening its proof. CATES already records attributable, expiring suppressions. These are young and not independently validated here, but they narrow the novel work.

The build case survives if Warrant stays narrow: build the effective architecture contract compiler, completeness accounting, four-facet verdict, ruling lifecycle, semantic widening classifier, census, and invalidation model. Reuse analyzers, compiler visibility, SARIF, Statement v1, VSA fields, and existing signing backends. If Warrant instead becomes another graph extractor, another generic policy language, or another bespoke attestation envelope, much of it already exists and should be deleted in favor of adapters.
