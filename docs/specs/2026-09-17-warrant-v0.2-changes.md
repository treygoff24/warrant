# What changes in Warrant draft 0.2

Status: proposed revision, 2026-09-17. Astra revised the spec after Trey's approval of the review direction. Fable review and final ratification are still pending. No implementation plan or build has started.

## The product stays focused on better architectural decisions

Warrant should help an agent understand what already exists before it writes more code, then check the result against rules the agent cannot quietly relax. The revision makes that the first complete experience, rather than building most of the checking machinery before making the map useful.

The main spec's section 1.7 now follows grouped undo in Atlas from the first question through final acceptance. It names what the agent should learn, which existing interface it should discover, what evidence it owes, and what Trey sees at the end. The example paths remain illustrative until the build work selects an actual Atlas revision.

## What stays

The architecture map, domain-specific contracts, human-signed rules, visible gaps in analysis, and verifiable receipts all stay. The result still separates four questions: did the code meet the checked rules, could Warrant examine the necessary parts, does the required evidence exist, and is human approval still needed?

Useful borrowed tools also stay. Git identifies source; compilers and parsers supply code facts; ast-grep matches code patterns; existing tests, Fallow, coverage, and mutation tools provide their own results. SQLite stores the map, and SSH tools sign records. Warrant does not rebuild those products.

## What changes

### Useful guidance comes first

The initial map includes a minimal census, ordinary-language questions, existing interfaces, and relevant examples. It must handle a request whose words differ from the code's names. It must also distinguish several plausible owners, no match, and incomplete analysis. "We did not find it" cannot become "it does not exist."

A proposed change is a question Warrant answers. It is never a task Warrant stores or manages. Existing tools still decide who does the work and in what order.

### The checking claims get narrower and more honest

Finding a call named `plan()` does not prove that authorization protects an operation. Seeing the known email adapter's callers does not prove no other email route exists. Recognizing one database-write pattern does not prove it sees every write.

The spec now requires each check to state exactly what it establishes. Stronger requirements need the corresponding evidence, such as an executed test showing that a denied request produces no effect. An explanatory footnote cannot turn a weak check into a strong one. Linked parts of a feature are reported separately from evidence that the feature works.

### Acceptance depends on protected execution, not convincing paperwork

A source hash and a JSON report cannot prove who ran a test or which files it used. The final gate therefore requires evidence from an approved runner that actually executed the selected source. Its controlling program, configuration, and signing credentials must be protected from candidate code.

Warrant uses existing isolation and runner tools for this. It does not become a CI service or sandbox product. Choosing and verifying that arrangement remains necessary before claiming Atlas has an authoritative gate.

### Rules stay stable while the code changes

The signed policy identifies the rules themselves. Applying those rules to new code produces a separate list of checks. Adding a source file under an unchanged rule should not make Trey sign the same rule again.

Actual rule changes still need approval, including proposed stricter rules that would affect everyone. Two policies producing the same result on today's code is not enough to call them equivalent: they may treat tomorrow's code differently.

### Combined code gets fresh evidence

Other tools combine branches. Warrant checks the supplied result. The first version requires fresh evidence when that combined source differs from the source previously tested. An import graph can miss fixtures, migrations, generated files, and service inputs, so it is not a safe shortcut for reusing old test results.

### Model advice is optional and nonblocking at first

The typed model-advice interface stays. The recommendation is to start with advice only, so a missing service or questionable opinion cannot block otherwise acceptable code. A later choice to require human review because of a model answer would block acceptance, and the spec now says that plainly.

## What leaves the first product

Work-management features are removed, not postponed: registered lanes, reports about overlapping assignments, repair packets, dependencies between repairs, task states, and Beads-specific exports or scripts. Warrant also leaves branch merging and package installation to existing tools.

Several expansions are postponed: DOT and standalone HTML diagrams, full Rust source-reference analysis, cross-tree test-evidence reuse, and a broad model-provider and calibration system. A small Cargo dependency check stays so the design is tested on something besides TypeScript.

## How integrations are judged

There is no blanket cut to external connections. Each must reduce the total work of implementing, connecting, checking, and maintaining the needed behavior.

The three proposed policy importers translate a repository's existing dependency-cruiser, eslint-boundaries, or Nx rules. They do not import somebody else's architecture. Keep the relevant importer if the first repository needs it; do not require all three before Warrant is useful. An existing checker can also keep supplying results without translating its configuration.

The same applies to test-report readers and model providers. If Atlas needs two formats, support two. If a maintained library makes several formats easy and reliable, use it. The objective is less total complexity, not fewer dependency names.

## What would show this worked

Passing Warrant's own tests proves the checker works as specified. It does not prove agents produce better software. The revised spec therefore requires a small comparison on held-out Atlas changes, with and without pre-edit context, using the same final checks.

The comparison records unnecessary new owners and interfaces, repair attempts, missed defects, useful reuse, human interventions, and the difficulty of a follow-on change. It includes cases where new architecture is justified. Fewer warnings is not success if the rules got weaker or the code got harder to maintain.

## What still needs judgment or proof

The recommended first-release policy is model advice only. A separate choice remains for deterministic style preferences: should a violation require human review by default, or merely provide advice? Architectural invariants remain enforced either way.

The protected runner arrangement needs a concrete deployment and verification. Permanent identifiers for signed records need an owned domain or the repository-based alternative. Real Atlas corpus artifacts stay private unless separately approved for publication. Other naming and packaging recommendations are collected in spec section 20.2 rather than treated as settled decisions.

This revision changes documentation, not runtime behavior. Compiler-reference feasibility, current dependency pins, real runner isolation, and the Atlas outcome comparison remain untested. Ratification precedes the existing writing-plans workflow; implementation still requires separate authorization.
